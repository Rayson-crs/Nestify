# Nestify 产品需求文档

> 文档版本：v0.2
> 当前状态（2026-09-17 / v1.8.1）：公开产品名是 Nestify，不再使用中文产品名。P0 主链路已在 Electron 落地：库扫描、搜索、整理四步预览、模板改名、重复隔离、任务回滚。P1/P2 仍按下文规划，不把媒体指纹、LLM、定时无人值守删除写成已交付。
> 状态：核心需求冻结草案 + 六大模块评审纳入（历史）
> 产品形态：Electron 桌面应用（Windows 优先，macOS 兼容）
> 核心关键词：规则匹配、极速索引、批量治理、安全预览、可回滚变更

---

## 1. 文档目的

本文档把“我想整理乱文件”收敛成一个可设计、可开发、可验收的文件管理系统。

Nestify 不是网盘客户端，也不是资源管理器替代品。它的目标是：对本地盘、移动硬盘、NAS 映射盘、任意目录树建立极速索引；再用一套统一、细粒度、可组合的规则引擎，完成搜索、筛选、重命名、去重、归类、目录整形、压缩包治理；并在执行前提供可预览、可抽样、可回滚的变更计划。

场景可以来自 NAS + 迅雷下载后的乱目录，但产品边界必须是通用文件管理。NAS 只是一类慢速、高延迟、嵌套混乱的存储源。

---

## 2. 问题定义

用户真正痛苦的不是“找不到某个文件”，而是这些事情同时发生：

1. 文件量大、目录深。系统资源管理器搜索慢、过滤弱、批量改名能力粗。
2. 下载产物形态混杂：文件夹、压缩包、临时文件、同名副本、多层套娃。
3. 正确信息可能藏在任意一层：外层文件夹名错、内层文件夹名对；文件夹名全错、视频/图片名对；名字全是 `1.mp4` / `2.jpg`，正确信息在上层目录。
4. 解压后压缩包还在，副本还在，用户不知道该删哪份。
5. 人工逐个打开、核对、改名、移动太慢，且容易误删。
6. 现有工具通常只做一件事：Everything 快搜、PowerToys 批量改名、duplicate cleaner 去重、目录整理脚本。它们彼此割裂，规则不能复用，也无法基于路径上下文做细粒度变换。

Nestify 要解决的核心问题是：

> 用一套规则系统，把“看见、判断、改名、移动、删除、归类”变成可重复执行的文件治理流水线，并且足够快、足够安全。

## 3. 需求合理性评估

### 3.1 合理且应作为核心的部分

| 需求 | 评估 | 原因 |
| --- | --- | --- |
| 扫描磁盘 / 指定目录并建立索引 | 必须做 | 没有索引就没有极速搜索，也没有批量分析的数据底座 |
| 极速搜索 | 必须做 | 这是用户进入系统的第一动作，也是规则命中结果的入口 |
| 灵活规则匹配 | 必须做，且是产品灵魂 | 乱目录的“正确信号”分散在路径、文件名、扩展名、元数据、内容指纹中，必须可组合抽取 |
| 细粒度批量重命名 | 必须做 | `a/b/c/a.txt -> b.txt / c.txt` 是典型路径上下文改名，现有工具几乎做不好 |
| 重复文件分析与保留策略 | 必须做 | 下载、解压、拷贝都会制造重复；必须先分析再决策，不能直接删 |
| 自动整理目录 / 归类 | 必须做，但要分阶段 | 自动归类价值高，误伤也高，必须先“计划预览”，后“执行” |
| 基于内部文件名反推外层文件夹名 | 必须做 | 下载场景高频：外层乱、内层对 |
| 图片 / 视频快速预览 | 必须做 | 规则再强也需要人眼确认；预览是审核闭环，不是附属功能 |
| Electron 桌面 exe | 合理 | 需要本地文件系统权限、后台索引、原生预览、批量 IO；Web 应用不合适 |

### 3.2 合理但必须加约束的部分

1. “自动整理”不能默认破坏原结构。任何自动动作默认生成 Change Plan，用户确认后才落地。
2. “智能总结文件夹名称”不能一开始就上大模型。第一版应先做规则抽取、频率统计、媒体元数据、最长公共有意义片段；LLM 只能作为可选增强。
3. “处理尽快”不能等于无限制并行写盘。NAS / SMB / USB 盘一并发就卡死，必须按存储类型限流。
4. “搜索极快”不能把所有内容都全文索引。默认索引路径、文件名、扩展名、大小、时间、哈希、基础媒体元数据；内容索引按类型和用户开关启用。
5. 去重不能只比文件名。同名不一定相同，不同名也可能相同。必须分层：名字相似、大小相同、快速哈希、完整哈希、媒体指纹。

### 3.3 当前想法里不够清晰、需要产品拍板的点

1. Nestify 是“治理工作台”，不是资源管理器克隆。默认界面应是：库 -> 搜索/规则结果 -> 变更计划 -> 预览确认，而不是再做一个 Explorer。
2. 自动归类的目标结构必须用户可定义。系统提供模板，不替用户发明唯一目录哲学。
3. 压缩包治理要独立成模块。乱源经常来自“已解压但仍保留压缩包”。
4. 规则必须可保存、可测试、可复用、可对目录增量执行。一次性正则脚本成不了产品。

结论：方向正确，核心抓得住。风险不在功能太多，而在“自动”和“快”没有安全边界。后续所有功能都必须服从三条铁律：

1. 规则先匹配，动作后执行。
2. 先生成计划，再写磁盘。
3. 所有破坏性操作可预览、可抽样、可回滚。

## 4. 产品定位

### 4.1 一句话

Nestify 是面向本地和局域网存储的规则驱动文件治理系统：极速索引，细粒度匹配，批量改名 / 去重 / 归类，并在执行前给出可审核的变更计划。

### 4.2 不是什么

1. 不是网盘同步盘。
2. 不是备份软件。备份可以后续做导出/快照，但 v1 不把备份当主线。
3. 不是通用视频播放器 / 图片浏览器。预览要快，但不做播放器生态。
4. 不是 NAS 套件。可以管理 NAS 映射盘，但不依赖 NAS 厂商 API。
5. 不是 Everything 的完整替代。Everything 是系统级文件名搜索；Nestify 是带规则和治理动作的工作台。可以学习其索引速度，但产品价值在“匹配后能改”。

### 4.3 目标用户

1. 个人重度下载用户：迅雷 / BT / 网盘转存后目录混乱。
2. 媒体整理用户：视频、图片、音频、字幕、封面散落。
3. 资料归档用户：课程、项目、扫描件、压缩包套娃。
4. 轻度专业用户：需要可重复规则，而不是每次手写脚本。

非目标：企业文档中台、权限审批流、多租户协同编辑。

### 4.4 成功标准

用户在 10 到 100 万文件规模下，可以做到：

1. 指定目录首次扫描后，文件名搜索接近即时返回。
2. 写一条规则，在结果里看到命中样本，而不是先改盘再后悔。
3. 对重复文件、压缩包残留、套娃目录、错误文件夹名，生成可理解的治理计划。
4. 执行后能一键回滚本次任务。
5. 同一套规则下次还能跑，且支持增量。

## 5. 设计原则

1. 规则是一等公民。搜索、筛选、重命名、移动、删除、归类都是规则的不同 Action。
2. 路径上下文是一等数据。不只看文件名，而看祖先目录、兄弟文件、目录内主文件、扩展名分布。
3. 快来自索引和增量，不来自每次全盘 walk 后当场正则。
4. 安全默认。删除默认进入隔离区或回收站；重命名/移动默认可回滚；自动规则默认 dry-run。
5. 人机共审。自动建议 + 快速预览 + 抽样确认。完全无人值守只能在用户明确开启的规则集上发生。
6. 存储感知。本地 NVMe、USB 硬盘、SMB/NAS 使用不同扫描、哈希、预览策略。
7. 可解释。每条改名/移动/删除都必须能回答：命中了哪条规则、用了哪个字段、为什么建议保留这一份。

## 6. 核心概念

### 6.1 Library 库

一个被 Nestify 管理的根范围。可以是整盘、某个目录、多个目录的集合。库有自己的索引、规则集、任务历史。

示例：

- `NAS-Downloads` -> `\\NAS\Download`
- `Movies` -> `D:\Media\Movies`
- `Inbox` -> `E:\Thunder`

### 6.2 Entry 条目

索引中的一个文件或目录。核心字段：

- `id`：稳定内部 ID
- `path` / `parent_path` / `ancestors[]`
- `name` / `stem` / `ext`
- `is_dir`
- `size`
- `mtime` / `ctime` / `atime`
- `drive` / `volume_id` / `protocol`（local / smb / usb）
- `mime` / `kind`（image / video / audio / archive / subtitle / document / installer / unknown）
- `depth`
- `child_count` / `file_count` / `dir_count`
- `hash_quick` / `hash_full`
- `media_width` / `media_height` / `duration` / `codec`（可选）
- `sidecar_refs`（字幕、nfo、jpg 封面等）
- `signals`：从路径和内容抽取出的结构化信号

### 6.3 Signal 信号

规则真正匹配的不是原始字符串，而是抽取出的信号。例如：

- `path.level[-1]` 当前名
- `path.level[-2]` 父目录名
- `path.level[-3]` 祖父目录名
- `path.keywords`
- `name.tokens`
- `name.seq` 如 `1` / `01` / `E01`
- `sibling.dominant_name`
- `children.dominant_video_name`
- `ext`
- `size`
- `hash`
- `media.title` / `media.duration`
- `archive.unpacked_dir_exists`

这是实现 `a/b/c/a.txt -> b.txt` 的关键：规则操作的是 `path.level[-2]`，不是“整个路径当字符串碰运气”。

### 6.4 Rule 规则

一条规则包含：

1. `match`：谁被选中
2. `extract`：从命中对象抽取哪些字段/捕获组
3. `guard`：额外约束，如仅视频、仅叶子文件、父目录匹配某模式
4. `action`：search highlight / rename / move / copy / delete / tag / group / nest-flatten
5. `preview`：如何展示建议结果
6. `safety`：冲突策略、是否允许覆盖、是否进入隔离区

规则必须能单独测试，也能组成 RuleSet。

### 6.5 RuleSet 规则集

有序规则列表，可带作用域、优先级、停止条件（first match / all match / until no change）。用于“下载收件箱夜间整理”这类可重复任务。

### 6.6 Change Plan 变更计划

一次治理任务落地前的中间产物。包含将要发生的 rename / move / delete / mkdir，以及冲突、风险、影响统计。用户可以：

- 全选执行
- 按组执行
- 排除某些条目
- 导出计划
- 执行后生成 Rollback Plan

### 6.7 Workbench 工作台视图

不是普通文件树，而是“当前问题”的工作区：重复组、规则命中组、套娃目录、压缩包残留、待命名项、待归类项。

## 7. 用户主路径

1. 添加库：选择盘符或目录。
2. 扫描建索引：先文件名和基础元数据，后台补哈希和媒体信息。
3. 搜索或打开问题视图：重复、套娃、压缩包、可疑命名、空目录。
4. 编写或套用规则：立刻看到命中样本和预览结果。
5. 快速预览文件内容，确认规则是否误伤。
6. 生成变更计划，处理冲突。
7. 执行。写入任务日志和回滚点。
8. 规则保存，下次对增量文件再跑。


## 8. 功能范围

v1.8.0 对照：P0 主链路已落地，但第 8 项视频快速预览仍是 file URL，不是 ffmpeg 缩略图。P1 里套娃拍平、sidecar 跟随改名、规则导入导出、隔离区已有基础实现；压缩包残留识别、媒体元数据、NAS 断点续扫、相似文件名去重仍未闭环。P2 全部仍是规划，包括 LLM、感知哈希、定时无人值守整理。

### 8.1 P0 必须做，没有这些就不叫 Nestify

1. 库管理与目录扫描
2. 极速文件名 / 路径搜索
3. 规则引擎 MVP（匹配 + 抽取 + 重命名 + 过滤）
4. 变更计划、冲突检测、回滚
5. 重复文件分析（大小 + 哈希）与保留策略
6. 批量重命名文件和文件夹
7. 路径层级改名（用父/祖目录名替换当前名）
8. 图片和视频快速预览
9. 基础文件操作：打开、定位、复制路径、移到隔离区
10. 任务日志

### 8.2 P1 第一版本就该具备，否则下载整理场景闭环不了

1. 压缩包检测与“已解压残留”识别
2. 套娃目录识别与拍平
3. 用子文件/子目录信号重命名父目录
4. 按类型 / 规则归类到目标结构
5. 相似文件名去重，不只是字节相同
6. 媒体基础元数据（时长、分辨率）
7. 规则集保存、导入导出
8. NAS / SMB 扫描限流和断点续扫
9. 回收站 / 隔离区删除
10. 空目录、无意义目录（`New Folder`、`未命名`、`新建文件夹`）治理

### 8.3 P2 明显增强竞争力

1. 内容感知预览：视频 sprite/缩略图条、图片网格、音频波形
2. 感知哈希 / 视频指纹，找出“同内容不同封装”
3. 字幕 / 封面 / nfo 等 sidecar 跟随重命名和移动
4. 规则调试器：逐步看捕获组、为什么没命中
5. 定时/监听增量整理
6. 多库联合搜索
7. 撤销树和时间线
8. 中文分词、谐音、错别字、繁简匹配
9. 可选 LLM 辅助：从一堆乱七八糟的内部文件名提议一个文件夹名
10. 压缩包内部索引（不先解压也能搜）

### 8.4 明确不做（v1）

1. 云端账号体系、多用户协作
2. 实时双向同步
3. 完整备份版本库
4. 破解/下载/做种
5. 把 Nestify 做成默认文件管理器替换
6. 无确认的全自动删除
7. 依赖特定 NAS 品牌 SDK

## 9. 缺失能力补齐

原想法已经覆盖“搜、改、删、归类、预览”。要成为一个能用的治理系统，还必须补这些：

### 9.1 安全与可回滚

1. Dry-run 默认开启
2. 变更计划
3. 冲突策略：skip / suffix / merge / abort
4. 事务日志：每条 IO 前后路径
5. 回滚
6. 隔离区：删除先搬到 `.nestify-quarantine` 或系统回收站
7. 保护名单：系统目录、指定目录、小于/大于某体积策略
8. 执行前抽样：随机打开 20 个将改名的文件预览

没有这些，批量删除和自动归类不可上线。

### 9.2 索引与增量

1. 首次扫描、增量扫描、校验扫描
2. 文件系统 watcher（本地）+ 轮询（NAS）
3. 断点续扫
4. 排除规则：`node_modules`、`$RECYCLE.BIN`、`.git`、缩略图目录
5. 扫描健康面板：速度、错误、权限拒绝、断连

### 9.3 规则工程能力

1. 规则测试：用样例路径验证
2. 规则覆盖率：多少条目被命中、多少被多条规则命中
3. 规则优先级和互斥
4. 捕获组命名
5. 内置函数：slug、去括号、去广告词、取最长公共前缀、取主文件名、补零、繁简转换
6. 规则模板：下载整理、电影目录、课程资料、图片按日期

规则如果只能写正则，用户会很快放弃。必须有可视化拼装 + 高级表达式双模式。

### 9.4 压缩包与下载残留

1. 识别 zip/rar/7z/tar/iso
2. 判断“旁边已经有同名解压目录”
3. 判断“压缩包是目录的完整备份”
4. 建议删除压缩包或删除解压目录
5. 识别迅雷/临时文件：`.xltd`、`.td`、`.!qB`、`.part`、`desktop.ini`、`Thumbs.db`
6. 识别校验文件：`.nfo`、`.sfv`、`.torrent` 是否保留

### 9.5 目录结构治理

1. 套娃：`MovieName/MovieName/MovieName.mp4` 拍平
2. 单文件目录是否保留
3. 空目录清理
4. 无意义中间层删除
5. 目录名从子项投票生成
6. 保持 sidecar 和主文件在一起

### 9.6 预览与审核

1. 图片预览：缩略图、原图
2. 视频预览：快速首帧 + 可拖动缩略图条，不求完整播放器
3. 音频预览
4. 文本/字幕预览
5. 压缩包内文件列表预览
6. 对比预览：两份重复文件并排
7. 大图/大视频不阻塞主搜索

### 9.7 性能与存储适配

1. 本地 SSD 和高延迟 NAS 分开策略
2. 哈希只对疑似重复组计算，避免全盘 SHA256
3. 预览缓存
4. 后台任务队列，前台搜索不被堵死
5. 内存上限和 SQLite/索引文件位置可配置

### 9.8 可观测性和解释性

1. “为什么这条被命中”
2. “为什么建议保留这份重复文件”
3. 任务报告：改了多少、跳过多少、失败多少
4. 错误分类：权限、路径过长、文件占用、网络中断

### 9.9 国际化与 Windows 现实问题

1. 超长路径
2. 非法字符 `\/:*?"<>|`
3. 大小写、扩展名大小写
4. 文件被占用
5. 符号链接 / junction / 硬链接，避免去重误删
6. Unicode 规范化、中日韩文件名
7. Windows 回收站 vs 网络盘无回收站

这些都是真实会翻车的点，必须写进需求，而不是开发时才发现。

## 10. 功能详细说明

### 10.1 库与扫描

#### 目标

把任意目录变成可搜索、可分析、可治理的库。

#### 功能点

1. 添加库：本机目录、盘符、UNC 路径、已映射网络驱动器。
2. 库设置：
   - 包含路径
   - 排除路径/模式
   - 最大深度
   - 是否跟随 symlink
   - 是否扫描隐藏/系统文件
   - 哈希策略：off / on-demand / duplicate-candidate-only / all
   - 媒体元数据策略
   - 预览缓存策略
3. 扫描模式：
   - Fast：walk + 文件名 + size + mtime
   - Standard：再补 kind、ext 分组、目录统计
   - Deep：哈希、媒体元数据、压缩包列表
4. 进度：文件数、目录数、字节数、当前路径、速度、ETA、错误数。
5. 暂停、继续、取消、断点。
6. 扫描完成后给出问题摘要：
   - 重复候选
   - 压缩包残留
   - 套娃目录
   - 空目录
   - 超长路径
   - 非法字符
   - 无意义名称
   - 单文件深层套娃

#### 验收

1. 100 万文件本地 SSD 首次 Fast 扫描可在可接受时间内完成，后续增量近实时。
2. NAS 断连后可继续，不把库标成损坏。
3. 排除规则确实不进索引。
4. 用户能看到每个扫描错误，而不是静默丢文件。

### 10.2 极速搜索

#### 目标

输入即过滤，规则命中也能复用同一套查询内核。

#### 查询能力

普通框支持：

1. 纯文本：子串匹配文件名
2. 空格分词：默认 AND
3. 路径搜索：`path:b/c`
4. 过滤语法：
   - `ext:mp4`
   - `type:video|image|archive|dir`
   - `size:>1gb`
   - `mtime:2024..2026`
   - `depth:<=3`
   - `dir:"Download"`
   - `has:subtitle`
   - `dup:true`
   - `name:"^\\d+$"` 正则
5. 作用域：当前库、当前目录、当前规则结果
6. 排序：相关度、mtime、size、path、name
7. 分组：按目录、按扩展名、按重复组、按规则

#### 结果交互

1. 虚拟列表，瞬间滚动
2. 显示路径面包屑
3. 右键：打开、定位、复制、加入规则测试集、加入变更计划
4. 多选后批量加入治理动作
5. 搜索结果可保存为智能视图

#### 技术方向

1. 文件名和路径使用倒排 + trigram / n-gram 索引
2. 热数据内存缓存，全量 SQLite / 自定义 mmap 索引
3. 查询线程和 UI 线程隔离
4. 输入 debounce + 增量 query
5. Windows 上可借鉴 USN Journal 做增量，但不作为唯一依赖，因为 NAS 没有 USN

#### 验收

1. 索引完成后，常见文件名查询在 50ms 级返回首屏。
2. 带 `ext:` / `size:` 的组合过滤不退化成全表扫描到卡死。
3. 规则命中结果和搜索结果能互相跳转。

### 10.3 规则引擎

这是产品内核。所有功能都应尽量表达为 Rule。

#### 10.3.1 规则模型

```text
Rule {
  id
  name
  enabled
  scope                # library / path glob / current selection
  match                # matcher tree
  extract              # named captures / signals
  guards               # additional predicates
  action
  on_conflict
  safety
}
```

Matcher 采用可组合树，不是单行正则：

```text
AND
  type = file
  ext in [mp4, mkv, avi]
  OR
    name regex "^\d+$"
    name in ["unpacked", "new folder"]
  parent.name regex ".+"
```

#### 10.3.2 匹配源

规则可从以下任意源取值：

1. `entry.name`
2. `entry.stem`
3. `entry.ext`
4. `entry.path`
5. `entry.ancestors[n]` 或 `parent` / `grandparent` / `root`
6. `entry.relpath`
7. `entry.size` / `mtime`
8. `entry.kind`
9. `dir.children.names`
10. `dir.children.main_media`
11. `dir.name_histogram`
12. `siblings.same_ext`
13. `archive.peer_dir`
14. `duplicate.group`
15. `media.*`
16. 自定义 extractors

#### 10.3.3 抽取与变换

用户例子：`a/b/c/a.txt` 改为 `b.txt` 或 `c.txt`

路径 `a/b/c/a.txt`：

- `level(0)=a`
- `level(1)=b`
- `level(2)=c`
- `level(3)=a.txt`

所以：

- 改为父目录名：`{ancestor(-1).stem}{ext}` -> `c.txt`
- 改为祖父目录名：`{ancestor(-2).stem}{ext}` -> `b.txt`

规则编辑器必须把这层语义做成可视化选择，而不是要求用户数路径。

内置变换函数：

1. `regex_capture`
2. `replace`
3. `trim`
4. `case`（lower / upper / title / keep）
5. `pad_number`
6. `take_number`
7. `remove_ads`（可配置广告词表）
8. `remove_brackets`
9. `normalize_whitespace`
10. `filename_sanitize`
11. `from_parent(n)`
12. `from_main_child`
13. `most_common_child_token`
14. `longest_common_prefix(children)`
15. `if_empty(default)`
16. `unique_in_dir`

#### 10.3.4 动作类型

1. `filter`：只搜索/标记
2. `tag`
3. `rename_file`
4. `rename_dir`
5. `move`
6. `copy`（默认谨慎，v1 可后置）
7. `delete_to_quarantine`
8. `flatten_dir`
9. `group_into_dir`
10. `attach_sidecar_follow`
11. `set_parent_name_from_children`

#### 10.3.5 规则编辑体验

双模式：

1. 引导式：选择对象类型 -> 选择匹配字段 -> 选条件 -> 选动作 -> 填模板
2. 高级式：表达式 / YAML / 正则

必须有：

1. 即时命中计数
2. 命中样本表
3. 前后对比列：`from` / `to`
4. 红色标冲突、非法名、空结果、循环重命名
5. 单条规则测试沙盒，输入一个路径立刻看输出
6. 保存为模板

#### 10.3.6 规则集执行语义

1. 顺序执行
2. 每条规则可设置 `stop_if_matched`
3. 目录改名后，后续规则看到的是计划中的新路径，不是旧路径。这点非常关键，必须在计划层做虚拟文件系统，而不是改一条刷一次盘
4. 最大迭代次数，防止规则互相改来改去

#### 验收

1. 用户不写代码，能完成“用父目录名替换无意义文件名”
2. 能完成“若文件名是数字，且祖父目录像作品名，则文件改名为祖父目录名 + 序号”
3. 能完成“目录内存在主视频时，把目录改成主视频名”
4. 规则 dry-run 与真实执行结果一致
5. 两条规则作用于同一文件时，计划里能看到先后顺序和最终名

### 10.4 批量重命名

规则引擎的一个高价值特化界面。

#### 模式

1. 查找替换
2. 正则替换
3. 插入前缀/后缀
4. 序号重整
5. 扩展名统一
6. 从路径层级取名
7. 从子项取名
8. 去广告词 / 去网站名 / 去括号垃圾
9. 模板改名：`{parent}-{stem}-{n:03}{ext}`
10. 大小写和空白规范化

#### 必须处理的细节

1. 文件和文件夹分开或混合，混合时先文件后目录或按深度从深到浅
2. 目录改名影响子路径，计划里一次性重写
3. Windows 非法字符自动清洗并提示
4. 目标重名冲突
5. 仅扩展名不同的大小写冲突
6. 预览 200+ 条不卡
7. 可按“将变的 / 不变的 / 冲突的”过滤


### 10.5 重复文件

#### 分层检测

1. L0 名称相同
2. L1 名称相似（编辑距离、去符号后相同、数字前缀不同）
3. L2 大小相同
4. L3 快速哈希（前 1MB + 大小 + 尾 64KB）
5. L4 完整哈希
6. L5 媒体指纹（P2）

默认只把 L2+L3 当强候选，L4 确认后再允许自动删除。

#### 分组展示

每个重复组显示：

1. 文件数、浪费空间
2. 路径分布
3. 时间、大小、分辨率、时长
4. 哪一份在“更干净的目录”
5. 哪一份名字更有意义
6. 哪一份更新
7. 是否有硬链接

#### 保留策略

内置策略可组合：

1. 保留最新
2. 保留最旧
3. 保留最大
4. 保留路径最短
5. 保留名字最长/信息量最高
6. 保留指定目录优先
7. 保留非压缩包
8. 保留已归类库，删除收件箱中的副本
9. 手动点选

动作：

1. 删除其余
2. 移动其余到隔离区
3. 硬链接替换（P2，需谨慎）
4. 仅标记不处理

#### 验收

1. 同内容不同文件名能被找出
2. 同名不同内容不会被当成重复删除
3. 网络盘哈希可取消或限速
4. 删除前必须看到将删列表和保留文件预览
5. 硬链接/同一 inode 不显示为浪费空间，或至少明确标注

### 10.6 目录整形与自动归类

#### 10.6.1 目录信号投票

对一个目录，收集：

1. 子文件名
2. 子目录名
3. 主媒体文件名（最大视频/最多同类）
4. 扩展名分布
5. 已有 nfo / 文件夹.jpg
6. 公共 token

生成建议名，并给出置信度。低置信度只建议，不自动执行。

典型规则：

1. 若目录名无意义，且存在唯一主视频，目录改为主视频 stem
2. 若子目录名高度一致，外层改成该名
3. 若内部文件都是 `1.mp4` 这种弱名，则不要用文件名污染目录名，改用更上层或保持并标记人工审核
4. 若目录内有多个不同作品信号，不要强行改成一个名字，改为拆分建议

#### 10.6.2 套娃拍平

识别：

- `A/A/A.mp4`
- `A/B/B.mp4` 且 A 无意义
- 单子目录且无其他有效文件

动作：提升一层，保留更有意义的那层名字。

#### 10.6.3 归类器

归类不是写死 `图片/视频/文档`。而是用户定义目标树 + 规则。

内置模板：

1. 按类型：`Images/` `Videos/` `Archives/` `Docs/`
2. 按扩展名
3. 按年份 `mtime.year`
4. 按来源目录
5. 按规则抽取的作品名
6. 自定义：`Media/{kind}/{name}/`

归类动作默认 `move`，可先生成 copy plan，但 v1 不建议真实复制以免爆盘。

#### 10.6.4 下载收件箱工作流

针对迅雷/NAS 下载目录提供预设 RuleSet：

1. 忽略临时文件
2. 识别压缩包和解压目录
3. 拍平一层套娃
4. 无意义文件名改用目录信号
5. 无意义目录名改用内部主文件
6. 重复副本进入重复工作台
7. 不自动删除，只生成建议

### 10.7 压缩包治理

功能点：

1. 索引压缩包为 kind=archive
2. 同级或解压后目录匹配
3. 比较压缩包大小、内部文件数（能读则读）与目录内容
4. 状态：
   - `archive_only`
   - `dir_only`
   - `both_present_same`
   - `both_present_different`
   - `partial_extract`
5. 建议：删包留目录、删目录留包、都保留、都送审
6. 不在 v1 做解压执行，除非后续单列。v1 以识别和清理残留为主

### 10.8 预览系统

#### 原则

预览是为了让人快速确认规则和重复决策，不是做播放器。

#### 功能

1. 图片：缩略图网格、选中大图、下一张极快
2. 视频：封面、hover 预览、短缓存、按时间抽样帧
3. 音频：短播放
4. 文本/字幕/json/nfo：先能看
5. 目录：子项分布图，主文件是谁
6. 重复对比：左右两份
7. 改名前对比：旧路径 / 新路径 / 预览

#### 性能

1. 独立预览队列
2. 缩略图磁盘缓存
3. NAS 上先显示占位，不卡列表滚动
4. 超大视频只解码关键帧
5. 预览失败要明确原因：codec / permission / network

### 10.9 变更计划、执行、回滚

任何写操作都走同一流水线：

1. Match
2. Plan
3. Validate
4. Confirm
5. Execute
6. Report
7. Rollback

Plan 条目至少包含：

- `op`: rename / move / mkdir / quarantine / delete
- `from`
- `to`
- `rule_id`
- `reason`
- `risk`: overwrite / long_path / occupied / network / ambiguous
- `confidence`

Validate 检查：

1. 目标是否已存在
2. 路径是否超长
3. 字符是否合法
4. 是否改到库外
5. 是否触碰保护路径
6. 文件是否被占用
7. 目录改名循环
8. 磁盘空间（move 跨卷实际是 copy+delete）

Execute 要求：

1. 可取消
2. 失败继续或失败中止可配
3. 跨卷 move 明确提示
4. 写操作单线程或按磁盘分组限流，搜索仍可用
5. 完成后给报告

Rollback：

1. 以任务为单位
2. 只回滚成功项
3. 若回滚目标又被占用，进入冲突列表
4. 删除类回滚依赖隔离区，不承诺从系统回收站完美还原网络盘

### 10.10 工作台问题视图

首页不应只是文件树。应直接暴露“待治理问题”：

1. 重复组
2. 压缩包残留
3. 套娃目录
4. 无意义名称
5. 空目录
6. 超长路径 / 非法字符
7. 规则命中但置信度低
8. 扫描错误
9. 最近任务

每个问题视图都是同一套结果表 + 预览 + 生成计划。

## 11. 关键用户故事

### US-01 极速找到文件

作为用户，我添加 `\\NAS\Download` 后，输入作品名或文件名片段，能立刻看到所有命中，并按视频/图片/压缩包分组。

### US-02 数字文件名借用上层目录

目录 `A/B/C/1.mp4`，文件名无信息。我希望规则：若 stem 是纯数字，则改成 `{ancestor(-1)} - {stem}{ext}` 或直接 `{ancestor(-2)}{ext}`。我要先看 50 条预览，再执行。

### US-03 外层文件夹名很乱，内层是对的

`乱码123/正确名称/xxx.mp4`，系统建议把外层改成“正确名称”，或拍平成 `正确名称/xxx.mp4`。

### US-04 文件夹名全错，视频名是对的

`新建文件夹/电影名.mkv`，系统建议文件夹改为 `电影名`。

### US-05 解压后压缩包还在

`电影名/` 和 `电影名.zip` 同时存在且内容匹配，系统给出重复浪费空间，并建议删 zip。我可以一键加入隔离区。

### US-06 重复下载

同一视频在不同子目录出现两份。系统按哈希分组，默认保留路径更规整、名字更完整的一份，另一份进入隔离区。我可以切换“保留最新”。

### US-07 自动归类

规则：所有 `ext in image` 且不在 `Pictures/` 下的文件，计划移动到 `Pictures/{year}/{name}`。执行前我能看到目录创建列表。

### US-08 快速审核

规则命中 3000 个改名项。我用缩略图/视频首帧快速扫 30 个样本，发现广告词没去干净，回去改规则再生成计划。

### US-09 误操作回滚

我执行了拍平目录，发现拍过了。任务页一键回滚，结构恢复。

### US-10 规则复用

我把“下载收件箱清理”保存为 RuleSet，以后只对新增文件增量跑。

### 12.1 主导航

v1 规划导航是：库、搜索、规则、问题（重复/压缩包/套娃/脏名）、计划/任务、设置。

3. 整理
4. 改名
5. 重复
6. 任务
7. 设置 / 关于

## 13. 技术架构方向

### 13.1 总体分层与技术栈冻结

v1 技术栈已冻结为：**Electron + Node.js + TypeScript + React + shadcn/ui**。详细说明见 [02-tech-stack.md](./02-tech-stack.md)。六大模块纳入规格见 [01-six-core-modules.md](./01-six-core-modules.md)。

不上 Rust core。扫描、索引、规则、计划、执行全部用 TypeScript 跑在 Electron 主进程和 Node worker 里。schema、规则 YAML、IPC 必须稳定，以后若真要 native 加速，只替换 worker，不推翻产品层。

```text
Renderer (React + shadcn/ui + Tailwind)
  搜索 / 文件 / 整理 / 改名 / 重复 / 任务 / 预览
        |
preload (contextBridge, 白名单 IPC)
        |
Electron Main
  窗口、菜单、shell.showItemInFolder、shell.trashItem、任务调度
        |
Node Workers / utilityProcess
  已落地：query / writer / thumbnail / library-removal
  目标：scanner / hasher / rule-vm / planner / executor
        |
node:sqlite (WAL) + FTS5 + trigram
preview cache (%APPDATA%/Nestify/cache/thumbnails)
quarantine
        |
Filesystem / SMB
```

UI 组件：shadcn/ui。虚拟列表必须用 TanStack Virtual，不能让普通 Table 渲染十万行。当前搜索结果先分页。领域逻辑放 `packages/core`，可脱离 Electron 单测。v1.8.0 索引是 Node 22 `node:sqlite`，不是 better-sqlite3。

### 13.2 索引方案

主存储 SQLite：

- `entries(id, parent_id, name, stem, ext, is_dir, size, mtime, ino, dev, kind, hash_quick, hash_full, ...)`
- `paths` 物化路径或通过 parent 链重建
- `fts_names` FTS5 文件名/路径
- `signals` 可缓存的抽取结果
- `dup_groups`
- `jobs` / `job_ops`
- `rules` / `rulesets`

附加：

- 文件名 trigram 表或自定义倒排，解决“极快模糊搜”
- 预览缓存目录，按 entry_id+size+mtime 存 WebP
- WAL 模式，扫描写入与查询并发
- Node 侧目标曾是 better-sqlite3；v1.8.0 实际使用 `node:sqlite` 的 `DatabaseSync`

增量：

- 本地 NTFS：USN Journal 可选加速
- 通用：mtime/size/ino 对比
- NAS：按目录分块 walk，记录 cursor

### 13.3 扫描器

1. 迭代 walk，不递归爆栈
2. 生产者-消费者
3. 按设备限流：
   - local nvme: 高并发
   - hdd: 低并发顺序
   - smb: 更低并发、更大 timeout、可重试
4. 权限错误记下来继续
5. 路径规范化、Win32 long path prefix `\\?\`
6. 不跟随危险 junction 循环，检测 visited inode/dev

### 13.4 查询引擎

搜索框解析成 AST，转成：

1. FTS / trigram 候选
2. SQLite 过滤（size、type、mtime）
3. 内存二次精排

规则 match 尽量能下推到索引字段；不能下推的（如复杂 sibling 统计）在候选集上算。

### 13.5 规则 VM

需求：确定性、可调试、快。

方向：

1. 规则编译成中间表示，而不是每次解释一棵超深 UI 树
2. 对每个 entry 提供只读 View：name、ancestors、cached signals
3. 禁止规则直接 IO。需要 sibling/children 时走索引，不现场 readdir，除非 signal 缺失
4. 提供 trace：每个 predicate true/false，每个 capture 值
5. 沙盒超时和内存限制

规则序列化格式建议 YAML，便于 Git 管理和导入导出。

### 13.6 计划器

核心技巧：虚拟目录树。

执行规则时不写盘，先在内存/临时表中应用路径变换，检测：

1. A 改名为 B，B 改名为 C
2. 两个文件改到同一目标
3. 父目录改名后子文件目标跟随
4. 删除目录和改其子项的冲突

计划输出可排序的 IO 序列：先深层 rename，再浅层，或统一成 move ops。

### 13.7 执行器

1. 使用 `rename` 原子性尽量保持同卷
2. 跨卷自动降级 copy + verify + delete
3. 失败写 `job_ops.status=failed`
4. 占用中的文件进入 retry 队列
5. NAS 上 verify 用 size+mtime 或 quick hash，不只看 copy 返回成功

### 13.8 预览服务

独立 worker：

- 图片用 `sharp` 生成 128x128 WebP
- 视频用 `fluent-ffmpeg` 抽第一帧；ffmpeg 作为可选组件
- 任务队列优先级：当前选中 > 当前屏缩略图 > 后台预生成
- 缓存淘汰 LRU
- NAS 上缩略图并发 1-2，出屏取消

### 13.9 性能目标（设计指标，不是拍脑袋承诺）

以 Windows + 本地 NVMe + 100 万文件为参考：

| 场景 | 目标 |
| --- | --- |
| Fast 扫描 | 尽量接近磁盘枚举上限，UI 保持可交互 |
| 增量扫描已建库 | 秒到数十秒级，取决于变更量 |
| 文件名搜索首屏 | < 50ms |
| 规则 dry-run 10 万命中生成计划 | 秒到十几秒，需进度条 |
| 重复候选（先 size 分组） | 不先全盘哈希 |
| 缩略图当前屏 | 滚动不卡，NAS 允许占位 |

NAS 场景所有写指标都要降级，并在 UI 标明“当前库是高延迟存储”。

### 13.10 技术风险

1. Electron 包体和 ffmpeg 体积
2. SMB 上 watcher 不可靠
3. 超长路径和非法 Unicode
4. 百万级 FTS 的磁盘占用
5. 规则用户门槛
6. 误删除带来的信任崩溃
7. 预览解码拖垮 NAS
8. 目录改名后索引失效
9. Node worker 在百万文件扫描时的内存和 GC 抖动

对应策略：core 与 shell 分离、默认 dry-run、隔离区、存储策略档位、计划层虚拟树、预览限流、扫描流式写入 SQLite 而不是在 JS 里攒整棵树。v1 用 Node 换迭代速度；性能墙出现后再替换 worker，不替换产品契约。


## 14. 数据与规则示例

### 14.1 用祖父目录给文件改名

输入：`a/b/c/a.txt`

路径层级：

- `ancestor(-1)` = `c`
- `ancestor(-2)` = `b`
- `ancestor(-3)` = `a`

规则：

```yaml
name: rename-file-to-grandparent
match:
  all:
    - { field: is_dir, eq: false }
extract:
  grandparent: { from: ancestor(-2).stem }
  parent: { from: ancestor(-1).stem }
  ext: { from: ext }
action:
  type: rename_file
  template: "{grandparent}{ext}"   # -> b.txt
# template: "{parent}{ext}"        # -> c.txt
safety:
  skip_if_target_exists: true
```

产品里 ancestor 选择必须可视化，用户点“用上两级目录名”，而不是手写 `-2`。

### 14.2 无意义文件名使用父目录 + 序号

```yaml
name: numeric-video-from-parent
match:
  all:
    - { field: kind, eq: video }
    - { field: stem, regex: "^[0-9]+$" }
action:
  type: rename_file
  template: "{ancestor(-1).stem} - {stem:pad(2)}{ext}"
```

`正确名称/1.mp4` -> `正确名称/正确名称 - 01.mp4`

### 14.3 用主视频改文件夹

```yaml
name: rename-dir-from-main-video
match:
  all:
    - { field: is_dir, eq: true }
    - { field: name, regex: "^(新建文件夹|未命名|New Folder|download|乱码.*)$" }
    - { field: children.main_kind, eq: video }
    - { field: children.video_count, eq: 1 }
action:
  type: rename_dir
  template: "{children.main_video.stem}"
```

### 14.4 压缩包残留

```yaml
name: archive-already-extracted
match:
  all:
    - { field: kind, eq: archive }
    - { field: peer_dir.exists, eq: true }
    - { field: peer_dir.same_payload_confidence, gte: 0.9 }
action:
  type: quarantine
  reason: "已存在解压目录"
```

### 14.5 套娃拍平

```yaml
name: flatten-single-child-wrapper
match:
  all:
    - { field: is_dir, eq: true }
    - { field: children.dir_count, eq: 1 }
    - { field: children.useful_file_count, eq: 0 }
    - { field: name, in_list_from: "meaningless_dir_names" }
action:
  type: flatten_dir
  keep: "child_if_child_name_more_informative"
```

### 14.6 按规则归类图片

```yaml
name: file-images-by-year
match:
  all:
    - { field: kind, eq: image }
    - { field: relpath, not_prefix: "Pictures/" }
action:
  type: move
  template: "Pictures/{mtime.year}/{name}"
```

## 15. 非功能需求

### 15.1 性能

见 13.9。补充：UI 任何时候都要能取消任务；不允许扫描把窗口冻住。

### 15.2 可靠性

1. 崩溃后索引可恢复
2. 执行中崩溃可从 job log 知道改到哪
3. 不在扫描时把整棵树持有在 JS 内存里

### 15.3 安全

1. 默认不访问系统盘关键目录
2. 保护路径清单
3. 不上传用户文件到云端
4. LLM 若启用，只发送已抽取文本信号，明确开关
5. 规则导入要当代码一样看，不能默认执行外部规则集的 delete

### 15.4 可维护性

1. 核心引擎与 UI 解耦
2. 规则 YAML 有 schema
3. 关键算法有单测：rename plan、flatten、duplicate grouping、path sanitize、占位符链式函数
4. 用 fixture 目录做端到端测试
5. UI 用 shadcn 组件，但表格必须虚拟滚动

### 15.5 本地化

1. 先中文界面
2. 路径永远按系统原样显示，不擅自转码显示乱码还当正确名去改
3. 保留显示名和内部字节名的差异提示

### 15.6 打包

1. Windows x64 portable exe，输出 `apps/desktop/release/Nestify-v${version}.exe`。NSIS 安装器不是当前发行形态。
2. 可选 ffmpeg 组件
3. 索引和缓存放在用户数据目录
4. 库配置可导出

## 16. 权限、平台与存储现实

Windows 优先，因为 NAS 映射和迅雷用户主要在 Windows。

必须处理：

1. `\\?\` 长路径
2. 需要时请求管理员权限，但不能默认管理员运行
3. 网络驱动器在不同权限会话下不可见
4. 文件占用（视频正在播、迅雷正在校验）
5. 只读 NAS 目录：计划可生成，执行要提前失败
6. 断开的映射盘
7. 卷序列号变化导致库根失效

macOS 后续：权限书签、APFS clone、大小写敏感盘差异。

## 17. 里程碑建议

### M0 骨架

Electron + React + shadcn 壳、库添加、Fast 扫描、SQLite 索引、文件名搜索、虚拟结果表、图片预览。v1.8.0 已完成壳、库、扫描和搜索；索引是 `node:sqlite`，图片预览是 `nativeImage`，不是 better-sqlite3 / sharp。

### M1 规则 MVP

可视化匹配、ancestor 字段、rename dry-run、计划、执行、回滚、非法名/冲突。

### M2 治理闭环

重复文件、隔离区、套娃拍平、目录名从子项生成、压缩包残留识别、视频预览。

### M3 可复用

规则集、增量扫描、NAS 限流、问题工作台、任务报告、内置模板。

### M4 增强

sidecar 跟随、媒体指纹、压缩包内部索引、可选 LLM 命名、监听自动化。

建议的开发顺序不是“先做自动整理”，而是：

```text
索引/搜索 -> 规则匹配预览 -> 安全执行/回滚 -> 去重/压缩包/套娃 -> 自动归类模板
```

没有前三层，后面的自动化都是在赌用户磁盘。

v1.8.0 里程碑对照：M0 和 M1 主链路已落地（扫描、搜索、模板改名、计划、执行、回滚）。M2 完成重复隔离、隔离区和整理拍平基础，压缩包残留识别与视频抽帧未闭环。M3 有规则导入导出和增量扫描，没有 NAS 限流、问题工作台和定时整理。M4 仍是规划。

## 18. 验收标准总表

一版可称为可用，至少满足：

1. 能添加本地目录和 UNC 目录为库并完成扫描
2. 扫描后搜索文件名足够快，不卡 UI
3. 能用规则把 `a/b/c/a.txt` 预览改成 `b.txt` 或 `c.txt` 再执行
4. 能批量改文件名和文件夹名，失败可回滚
5. 能找出大小+哈希相同的重复文件，按保留最新/保留一份执行隔离
6. 能识别无意义目录名并用内部主文件建议新名
7. 能快速预览图片，能看到视频首帧或短预览
8. 任何删除都不直接永久消失，除非用户在设置里明确关闭隔离区且二次确认
9. 规则可保存再次执行
10. NAS 高延迟下系统仍响应，不因为预览或哈希卡死

## 19. 规则系统功能点方向（给设计/研发拆任务用）

### 19.1 Matcher

- 等于 / 包含 / 前缀 / 后缀 / 正则 / 空 / 数字 / 无意义名
- 扩展名集合、类型集合
- 大小/时间比较
- ancestor(n) 任意层级
- children / siblings 聚合条件
- 逻辑 AND / OR / NOT
- 作用域 glob

### 19.2 Extractor

- 正则命名捕获组
- 路径层级字段
- 主子文件
- 公共前缀/公共 token
- 媒体元数据
- 自定义词典（广告词、无意义文件夹名）

### 19.3 Action

- 过滤、标记、改名、移动、隔离、拍平、归类、跟随 sidecar

### 19.4 Safety

- dry-run
- 冲突策略
- 保护路径
- 置信度阈值
- 影响上限（超过 N 条必须人工确认）
- 计划层虚拟 FS

### 19.5 UX

- 可视化拼装
- YAML 高级模式
- 即时样本
- from/to 对照
- 命中解释
- 规则测试沙盒
- 模板

这一节的意思是：后续不要把“搜索页”“重命名页”“去重页”做成三套互不相通的逻辑。底层全是 matcher + extractor + action + plan。页面只是不同皮肤。

## 20. 开放问题

这些问题不阻塞文档，但实现前要定默认值：

1. 默认删除是系统回收站还是 Nestify 隔离区？已定：本地优先 `shell.trashItem`，失败则进隔离区；网络盘/UNC 强制隔离区。严禁静默物理删除。
2. 自动归类默认模板是按类型还是按“作品/事件”？已定：内置“默认下载整理”方案，全部 Dry-Run；按类型移动到 `Videos` 的规则默认禁用，且目标是库内目录不是盘符根。
3. v1 core 用 Rust 还是先 Node worker？已定：Node + TypeScript + shadcn。Rust 不进 v1。
4. 是否索引文件内容？建议维持：v1 不做通用全文，只做文件名、路径、媒体元数据、压缩包列表。
5. 是否允许规则自动定时执行？建议维持：M3 才开放，且默认只生成计划不落盘。
6. 重复文件“保留最新”的最新是 mtime 还是下载时间？已定：默认 mtime，可改。
7. 文件夹改名是否级联更新已保存规则里的绝对路径？建议维持：规则作用域尽量用库相对路径。
8. 预览是否内置 ffmpeg？已定：可选组件，未安装时图片预览仍可用，视频退化为图标+系统打开。
9. 覆盖冲突要不要密码确认？已定：不要密码框。覆盖默认关闭，需显式确认“覆盖 N 个文件”。

## 21. 结论

原需求成立：这不是又做一个资源管理器，而是做一个以规则匹配为内核的本地文件治理工作台。

必须抓住的优先级：

1. 极速索引与搜索
2. 细粒度、可组合、可调试的规则引擎，尤其是路径层级信号
3. 变更计划 + 预览审核 + 回滚
4. 重复、压缩包残留、套娃、脏命名这些高价值问题视图
5. 对 NAS 这类慢存储保持克制

不要一开始就追求全自动智能整理。智能只负责提议，规则负责表达，计划负责安全，执行负责快。这四层分开，Nestify 才既快又不会把用户磁盘整理废。

一句话产品公式：

```text
Index (fast see)
  + Signals (path/name/meta/hash)
  + Rules (match/extract/action)
  + Plan (preview/conflict/rollback)
  = File Governance Workbench
```
